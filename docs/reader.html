在线博客管理系统 · 技术文档

项目 5 / 两周行动计划 · Java 方向
v1.0 · 2026-11-20 · Spring Boot 3.2.5 + MyBatis 3.0.3 + H2 + 手写 JWT + Vue 3
请求从浏览器进来，先过安检口验通行证，Controller 收和回，Service 定规则，Mapper 翻成 SQL，H2 存数据；中间加了一层缓存，重复的问题不用每次都问数据库。

0. 这份文档怎么读

前四个项目用的是 Python / Django，这个项目第一次换到 Java / Spring Boot。但骨架是同一套：都是「路由 → 视图 → 模型 → 数据库」，只是每个零件的名字变了。

文档从用户能点什么开始，接着是请求怎么走、代码分几层，最后才进到 JWT、SQL、缓存这些细节。专有名词第一次出现时用括号解释。只想弄清「做了什么」，读第 1、2、3、14 节；要动手改代码再往下看。

1. 这个项目交付了什么

一个能真跑、能点、能写数据的在线博客系统，外加一块「把内部动作摊开给你看」的演示看板。

白话：所谓「项目」，不是一堆代码文件，而是「有人点一下 → 有东西真的变了 → 还能看见它怎么变的」这条闭环。看板就是把这条闭环画出来。

2. 从点一下开始：一次请求的完整往返

以「点开一篇文章」为例，浏览器只发了一行：

GET /api/articles/7/

它走过这六站：

站谁负责做了什么
① 浏览器static/app.js 的 request()拼好 URL，用 fetch 发出去；带上 Content-Type: application/json
② TomcatSpring Boot 内嵌服务器监听 8003，把 HTTP 报文变成 Java 里的 HttpServletRequest
③ 安检口AuthInterceptor.preHandle()判断这是否是需要登录的操作；GET 一律放行，写操作要验 JWT
④ ControllerArticleController.detail()从 URL 里取出 id=7，调用 Service，把结果包进 ApiResult
⑤ ServiceArticleService.detail()先问缓存：有就直接返回（HIT）；没有就查库、浏览量 +1、写回缓存（MISS）
⑥ Mapper → H2ArticleMapper.findById()把方法调用翻成一条 SELECT ... LEFT JOIN ...，H2 执行后把行填回 Article 对象

回来的时候倒着走一遍：对象 → ApiResult → Jackson 序列化成 JSON → HTTP 200 → fetch 解析 → Vue 的响应式数据更新 → 页面局部重绘，整页不刷新。

同时，安检口在 afterCompletion() 里记一条「方法 / 路径 / 状态码 / 耗时」，缓存层记一条「哪个 key、命中还是回源」。这两条流水就是看板下半部分的两张表。

白话：Controller 是前台，Service 是后厨，Mapper 是采购单，数据库 是仓库。前台不切菜，后厨不接客。

3. 技术栈与白话对照

名词在项目里白话解释

为什么 H2 不是 MySQL？ 计划里写的是 MySQL + Redis，但演示项目要能「一条命令跑起来」。H2 开 MODE=MySQL 后，SQL 方言、自增主键、常用函数都和 MySQL 一致；将来换真 MySQL，只改 application.yml 里的 spring.datasource 四行即可（第 15 节给了示例）。Redis 同理，代码里已经写好，探测到就自动启用。

5. 环境与一键启动

本机实测：Python 3.13、JDK 17.0.12（另有 JDK 26 但没进 PATH）、Node 22、无 Redis。Maven 原本没装。

start.py 的处理方式：

  1. find_java_home() 先看 JAVA_HOME，再试几个常见路径，最后退回 which java
  2. ensure_maven() 检查 tools/apache-maven-3.9.9，没有就从 Maven Central 下载 9MB 的 zip 解压到项目内
  3. 设置子进程 JAVA_HOME，执行 mvn -B -q -DskipTests package
  4. 执行 java -jar target/blog-app.jar --server.port=8003
python start.py                # 构建并启动
python start.py --build-only   # 只打包
python tests/e2e_api.py        # 另开一个终端跑 23 条回归

关键约束：Maven 和 H2 数据库都不入库（.gitignore 排除 tools/ 和 runtime/），换台机器 clone 下来重跑 start.py 即可；runtime/blogdb 只在表为空时灌演示数据，重启不会冲掉自己写的文章。

端口那行特意写成命令行参数 --server.port=8003，原因见第 16 节的踩坑复盘。

建表语句用 CREATE TABLE IF NOT EXISTS，spring.sql.init.mode=always 每次启动都执行但不会重建，所以数据能跨重启保留。article 表上有 status 索引，comment 表上有 article_id 索引。

Article 实体里还有 categoryName 和 authorName 两个字段，它们不是表字段，而是 LEFT JOIN 查出来的别名列。MyBatis 开了 map-underscore-to-camel-case，category_name 会自动填进 categoryName。

DemoSeeder 只在 article 表为空时灌 4 用户 / 4 分类 / 8 文章 / 6 评论；看板上的「重置演示数据」是显式按钮，才会清空文章、评论和事件流水（保留账号与分类）。

7. 三层架构：为什么非要分三份

以「发布文章」为例，请求 POST /api/articles/7/publish/ 的三层分工：

// Controller：只管接和回
@PostMapping("/{id}/publish/")
public ApiResult<Article> publish(@PathVariable Long id) {
    return ApiResult.ok(service.publish(id));
}

// Service：规则在这里
public Article publish(Long id) {
    Article a = articles.findById(id);
    if (a == null) throw new BusinessException(404, "文章不存在：" + id);
    articles.publish(id, LocalDateTime.now());   // status + published_at
    invalidate(id);                              // 缓存失效
    return articles.findById(id);
}

// Mapper：只写 SQL
@Update("UPDATE article SET status = 'published', published_at = #{now}, "
      + "updated_at = #{now} WHERE id = #{id}")
int publish(@Param("id") Long id, @Param("now") LocalDateTime now);

分开的好处很实际：

  • 校验「文章是否存在」只在 Service 写一次，任何入口都绕不过
  • 缓存失效只在 Service 写一次，不会出现「改了库忘了清缓存」
  • 换数据库只动 Mapper，Controller 一行不改
  • 测试可以只测 Service，不必起 Web 服务器

GlobalExceptionHandler（@RestControllerAdvice）兜住所有异常，把 BusinessException(404, ...) 统一变成 { "code": 404, "message": "..." }。前端只认一种响应形状，不用到处写 try/catch。

统一响应外壳：

{ "code": 0, "message": "ok", "data": { ... } }

code = 0 表示成功；业务错误用 code = 400/401/404/409，HTTP 状态仍可能是 200（由全局异常处理器返回）；只有安检口直接拒掉的未授权请求，HTTP 状态才是真正的 401。区分这两者是写测试时最容易踩的坑。

9. 安检口与手写 JWT

AuthInterceptor 拦所有 /api/**，规则是：

  • /api/health、/api/auth/login、/api/auth/register、/api/demo/**、/api/cache/**、/api/stats/** 放行
  • /api/auth/me 无论什么方法都要验 token（因为要往请求里塞 userId）
  • 其余 GET 放行；POST / PUT / DELETE 必须带 Authorization: Bearer <token>

JWT 不引第三方库，用 JDK 自带类实现：

// 1. 头：固定字符串做 Base64Url
// 2. 载荷：sub / uid / iat / exp
// 3. 签名：HMAC-SHA256(头 + "." + 载荷, 密钥)
String signingInput = HEADER + "." + body;
return signingInput + "." + sign(signingInput);

校验时做三件事：重新算一遍签名、MessageDigest.isEqual() 做常量时间比较（避免用响应时间猜签名）、检查 exp 是否过期。任一不过就返回 null，安检口写回 401 JSON。

白话：Session 像前台的登记本，服务器要留一份；JWT 像盖了钢印的通行证，服务器只验钢印、不存登录状态。代价是签发之后不好单独作废，所以有效期要短。

安全边界写清楚：这是教学实现。密码用带固定盐的 SHA-256（生产应换 BCrypt / Argon2），密钥写在配置文件（生产应从环境变量注入并定期轮换），没有 refresh token 和黑名单。第 15 节列了补齐清单。

10. MyBatis：SQL 到底怎么拼出来的

Mapper 是接口，没有实现类；@MapperScan 让 MyBatis 在启动时生成代理对象。SQL 写在注解里，参数用 #{...} 占位（PreparedStatement 绑定，不是字符串拼接，因此不会被 SQL 注入）。

筛选列表用 <script> 动态 SQL：

@Select({"<script>",
        COLUMNS, JOIN,
        "<where>",
        "  <if test='status != null'> AND a.status = #{status} </if>",
        "  <if test='categoryId != null'> AND a.category_id = #{categoryId} </if>",
        "  <if test='kw != null'> AND (LOWER(a.title) LIKE LOWER(CONCAT('%', #{kw}, '%')) ...</if>",
        "</where>",
        "ORDER BY a.id DESC LIMIT #{limit} OFFSET #{offset}",
        "</script>"})
List<Article> page(...);

<where> 会自动去掉第一个多余的 AND。Service 层把空字符串统一转成 null，所以 <if> 只需要判断 != null，避开 OGNL 里引号嵌套的麻烦。

@Options(useGeneratedKeys = true, keyProperty = "id") 负责把数据库生成的主键回填到对象里 —— 种子数据里评论要挂到刚插入的文章上，靠的就是这个。

11. 双后端缓存：探测、命中、失效

CacheService 里同时住着两个后端：

后端实现什么时候用
RedisStringRedisTemplate，带 TTL启动时探测 hasKey 成功，或看板手动切换成功
JVM 内存ConcurrentHashMap + 过期时间戳Redis 连不上（本项目默认状态），或运行中 Redis 挂了自动降级

app.cache.prefer = auto 时启动探测一次；探测结果缓存 5 秒，避免没有 Redis 的机器上每次刷新页面都等一次连接超时。

一次读取的动作序列：

  1. get(key) 问当前后端
  2. 有值 → 记 HIT，直接返回
  3. 没值 → 记 MISS，回源查库，记 WRITE 写回缓存
  4. 数据被改动 → evictPrefix("blog:list:") 之类记 EVICT，删掉相关 key

所有动作都写进 cache_event 表，/api/demo/state/ 取最近 24 条给看板画时间线。统计卡上的「缓存命中率」就是 HIT / (HIT + MISS)。

白话：缓存像便签纸。第一次不知道答案，翻账本（数据库）查完顺手抄在便签上；第二次直接看便签。但账本一改，便签就必须撕掉，否则会一直念旧答案。

ArticleService 里缓存的是 Jackson 序列化后的 JSON 字符串（注入 Spring 配好的 ObjectMapper，自带 LocalDateTime 支持）；反序列化失败就当没命中，重新查库 —— 坏缓存不会把页面搞崩。

12. 前端：Vue 3 与 13 步一键演示

页面只有一个 index.html，用本地 vue.global.prod.js 挂载，不引任何 CDN，断网也能打开。

app.js 里所有请求走同一个 request()：

async function request(path, opts = {}) {
  const headers = { 'Content-Type': 'application/json' };
  if (withToken && token.value) headers['Authorization'] = 'Bearer ' + token.value;
  const res = await fetch(path, { method, headers, body: ... });
  const json = await res.json();
  return { status: res.status, code: json.code, data: json.data, message: json.message };
}

onMounted 时并行拉 /api/demo/state/（统计、分类、事件、流水、技术栈）和 /api/articles/（列表）。Vue 的 ref 一变，模板里对应的数字、列表、徽章自动重绘。

「一键跑完整流程」是真的按次序发 13 个 HTTP 请求，不是写死的动画：

步动作想让人看见什么
1登录拿到 JWT，之后所有写请求都带上它
2不带 token 写文章安检口返回 401，安全规则真的生效
3-4连读两次分类第一次 MISS，第二次 HIT
5-6连读两次列表同上，缓存键不同
7新建草稿写操作成功，相关缓存自动失效
8发布draft → published
9再读列表缓存已失效，重新回源，新文章立刻可见
10-11写评论、读评论评论缓存的写入与命中
12读统计数字来自几张表的 COUNT
13删除演示文章把数据还原，可反复点击

带 ?demo=1 打开页面会自动跑这一串，便于分享和自动化验证。无头浏览器实测：13 步全部渲染，12 个 200 + 1 个预期 401，结束后文章数回到 8。

16. 踩坑复盘（8 条，按出现顺序）

① H2 的 AUTO_SERVER 与 DB_CLOSE_ON_EXIT 不能同时开。 第一次启动直接失败：Feature not supported: "AUTO_SERVER=TRUE && DB_CLOSE_ON_EXIT=FALSE" [50100-224]。单进程根本用不到 AUTO_SERVER（那是给多个 JVM 共享文件用的），去掉这两个参数即可。启动时报的错往往是最外层的一长串 BeanCreationException，要一路翻到最底下 Caused by 才是根因。

② 环境变量 SERVER__PORT=53555 把端口改了。 日志里 Tomcat 起在 53555 而不是 8003。查 env 发现宿主注入了 SERVER__PORT，Spring Boot 的宽松绑定把它当成了 server.port，优先级高于 application.yml。修法：启动命令显式加 --server.port=8003（命令行参数优先级最高），start.py 里也这么写。

③ GET 一律放行，把 /api/auth/me/ 也放过了。 前 3 条 e2e 失败：无 token 返回 {"code":401} 但 HTTP 200，带 token 也返回「请先登录」。原因是 needToken() 里「GET 放行」的判断在白名单之后，导致拦截器压根没验 token、也没把 userId 塞进请求。加一条 /api/auth/me 的例外提前返回 true 即可。

④ 环境代理会把 127.0.0.1 的请求转发出去。 这是项目 4 踩过、这里提前防住的坑：机器上有全局 HTTP_PROXY，requests / urllib 默认走代理，本地接口会拿到代理返回的 404。e2e_api.py 用 ProxyHandler({})，curl 验证一律加 --noproxy '*'。

⑤ 种子数据不能硬编码主键。 「重置演示」会清空文章再重灌，但 H2 的 AUTO_INCREMENT 不会回到 1，第一版把评论写死挂在 1L~5L 上，重置后评论就挂到了不存在的文章。改成 addArticle() 返回真实生成的主键，用 List<Long> ids 收集后再挂评论。

⑥ Redis 探测不能每次都做。 没有 Redis 时，每次 redisAvailable() 都要等一次连接超时；而 /api/demo/state/ 里会调两次，页面明显变慢。加了 5 秒的探测结果缓存，switchTo() 时强制重新探测一次。

⑦ 暗色主题下的灰色标签。 前几个项目踩过「白底白字」：暗色模式下 .pill-muted 如果只给背景不给文字色，就会变成浅底浅字。这次所有徽章变体都显式写了 background 和 color 两个变量，500px 手机截图复核通过。

⑧ 运行的 jar 会锁住文件，改完必须重启才生效。 Spring Boot 把静态资源打进 target/blog-app.jar，改了磁盘上的 static/app.js 不会立刻反映到页面上，Windows 上也不能直接覆盖正在运行的 jar。正确顺序是：停服务 → mvn package → 重启。这不是 bug，但很容易让人误以为「改了没用」。

第一次用 Java 写后端：我把「请求怎么走一圈」重做了一遍

2026-11-20 · 项目 5 复盘 · SpringBoot / MyBatis / JWT / 缓存 / Vue 3

前四个项目我都是用 Python + Django 写的：校园二手交易平台、订单通知幂等、大文件分片上传、接口自动化回归。写得越久越容易形成一种错觉——好像「后端」就长 Django 那个样子：urls.py 配路由，views.py 写函数，models.py 定义表，完事。

所以轮到计划里的 Java 方向时，我其实有点虚。SpringBoot、MyBatis、IoC、Bean 这些词我都能背，但没真正从零搭过一次。这篇文章记录的是：我怎么用两周计划里的第 5 个项目，把这套东西从「听说过」变成「能讲清楚」，以及中间被什么卡住过。

先给结论，省得读到最后才发现是一篇流水账：Django 和 SpringBoot 不是两套东西，是同一套骨架换了名字。 都是「浏览器发请求 → 安检 → 路由 → 视图 → 模型 → 数据库」，只不过 Java 这边把每一层都拆得更细、更显式。

一、第一关居然是「跑起来」

我原以为写代码最难，结果第一天全花在环境上。

我用 java -version 查，提示没这个命令；但 JAVA_HOME 明明指向 D:\jdk-26.0.2.1，C 盘还躺着一个 jdk-17。原来这两个 JDK 都在，只是没进 PATH。用完整路径调用就行了，不是什么大问题，但足够让一个新手怀疑人生半小时。

Maven 是真没装。按「尽量避免折腾环境」的原则，我没有往系统里装，而是下载了 9MB 的 zip 解压到项目里的 tools/，再用 start.py 统一调它。好处是仓库里不放二进制、换台机器 clone 下来一条命令能复原；坏处是第一次要等下载。这个取舍我很喜欢：环境改动留在项目内，不污染系统。

然后第一次 java -jar，直接起不来，日志刷了三屏。最上面是 BeanCreationException，一层层 Caused by 翻到最底下才看到真凶：

Feature not supported: "AUTO_SERVER=TRUE && DB_CLOSE_ON_EXIT=FALSE" [50100-224]

H2 不允许这两个参数同时开。AUTO_SERVER 是给多个 JVM 共享同一个数据库文件用的，我单进程根本不需要，删掉即可。这里学到一个很实用的习惯：Spring 的报错要倒着读，最上面那串通常只是「谁被连累了」，最底下那句才是起因。

改完又遇到一件更隐蔽的事：日志里 Tomcat 起在 53555，不是我配的 8003。env 一查，宿主环境注入了 SERVER__PORT=53555，SpringBoot 的宽松绑定把它认成了 server.port，优先级比 application.yml 高。最后我在启动命令里显式加了 --server.port=8003（命令行参数优先级最高），才算彻底定死。

这两件事都不难，但都是「不看日志就永远猜不到」的类型。我把它们写进了技术文档的踩坑复盘，因为它们比代码本身更像真实工作。

二、把 Django 的零件换成 Java 的名字

环境通了，我开始对着骨架做翻译：

我熟悉的 Django这次的 Java其实都在干一件事
urls.py@GetMapping / @PostMapping把 URL 指到某个方法
views.py@RestController收请求、返 JSON
手写业务逻辑@Service规则集中在一层
ORM / Model.objectsMyBatis Mapper 接口对象 ↔ 表行
models.pyentity/ 下的 POJO数据长什么样
MiddlewareHandlerInterceptor请求进来前统一拦一道
JsonResponseApiResult<T> + Jackson统一响应外壳
Session 登录JWT确认「你是谁」

真动手才发现，Java 这边「分三层」不是形式主义。比如发布一篇文章：Controller 只有一行 return ApiResult.ok(service.publish(id))；Service 里校验文章是否存在、改状态、写 published_at、清缓存；Mapper 里只有一条 UPDATE。

好处在改需求时特别明显：后来我想给「发布」加缓存失效，只改了 Service 一处，Controller 一行没动。如果全塞在一个函数里，就得满屋子找「还有哪个入口也改了库」。

MyBatis 的 <script> 一开始看着吓人：

<where>
  <if test='status != null'> AND a.status = #{status} </if>
  <if test='kw != null'> AND LOWER(a.title) LIKE ... </if>
</where>

后来想通了——它不是魔法，就是按条件拼字符串，<where> 帮忙去掉第一个多余的 AND，#{} 交给 JDBC 做参数绑定（所以不是字符串拼接，不会被注入）。Service 里把空字符串统一转成 null，<if> 就只用判断 != null，连 OGNL 引号嵌套的坑都绕开了。

三、JWT：手搓一遍才真的懂

登录这块我本来可以直接引 jjwt，一行依赖搞定。但我选了用 JDK 自带的 Mac 手搓 HMAC-SHA256，因为我想搞清楚那三段到底是什么。

写完才发现，JWT 简单得有点反直觉：

头.载荷.签名

头和载荷只是 Base64Url 编码，谁都能解开看，里面就是 {"uid":1,"exp":...} 这种明文。真正防篡改的是第三段：用只有服务器知道的密钥，对「头.载荷」算一次 HMAC，再把结果附上。校验时重新算一遍，用 MessageDigest.isEqual() 做常量时间比较（避免攻击者靠响应时间一点点猜签名），再看看 exp 过没过期。

所以「JWT 不需要在服务器存登录状态」这句话一下就具体了：服务器不记你，只认钢印。代价也随之而来——签出去的 token 在过期前不好单独作废，所以有效期要短，敏感操作要二次校验。

这里也埋了一个真实的 bug。我的安检口规则是「读接口公开，写接口要 token」，结果 /api/auth/me/ 是 GET，被一起放行了：拦截器压根没验，也没把 userId 塞进请求，Controller 只能无奈地返回「请先登录」。23 条端到端回归里挂了 3 条，一眼就定位到 needToken() 的判断顺序。加了「/api/auth/me 无论什么方法都要验」这条例外，全绿。

写测试最大的价值不是证明代码对，而是把这种「看起来合理、其实漏了」的地方逼出来。

顺带说清边界：密码我用的是带固定盐的 SHA-256，密钥写在配置文件里，也没有 refresh token 和黑名单。这些在教学项目里够用，但要上线必须换 BCrypt、环境变量注入密钥、加退出即失效。我在技术文档里专门列了「离生产还差什么」一张表，还写了「任意登录用户可改他人文章」这个已知缺口 —— 能主动讲清边界，比假装没有边界更专业。

四、缓存不是一个 Map 那么简单

计划里写的是 Redis，但这台机器没装 Redis。我没有跳过这部分，而是做成了双后端：启动探测一次，能连上就用 Redis，连不上自动回退 JVM 内存；页面右上角明确标出当前用的是哪个；运行中 Redis 挂了也会自动降级。

理由是：缓存的逻辑（什么时候读、什么时候写、什么时候失效）跟「用 Redis 还是用内存」其实是两件事，不该绑死。

真正费心思的是「失效」。ArticleService 里每次新建、修改、发布、删除，都要调 invalidate() 清掉三类 key：列表、这篇文章的详情、这篇文章的评论。少清一个，页面就会一直显示旧内容——这是缓存最经典也最容易被忽略的 bug。于是我干脆把每一次 HIT / MISS / WRITE / EVICT 都写进一张 cache_event 表，看板上直接画成时间线。

第一次读分类：MISS → 回源 → WRITE；第二次：HIT。发布文章之后：EVICT → 再读又变 MISS。这几行流水比任何文字解释都直观，我后来给它配了「一键跑完整流程」按钮，13 步真实 HTTP 请求按次序发，把这个节奏完整演一遍。

还有个小优化挺有意思：没有 Redis 时，每次探测都要等一次连接超时，而 /api/demo/state/ 会调两次，页面明显卡顿。给探测结果加了 5 秒缓存，只在手动切换后端时强制重探。这种「不改功能、只改体感」的修法，很值得记下来。

五、把内部动作摊开给人看

前四个项目我都配了可视化看板，这次延续了下来。原因很私人：我自己就是靠看板才把原理想明白的。

看板上有 6 张统计卡、一张四层架构流程图、13 步演示步骤、缓存事件时间线和 API 请求流水。所有数字都来自 GET /api/demo/state/ 这个聚合接口 —— 真实项目里前端会分别调五六个接口，演示项目为了「一眼看全」在服务端拼成一个大包裹，这有个正经名字叫 BFF（给前端定制的聚合层）。

前端用本地 Vue 3，不引 CDN，断网也能打开。app.js 里所有请求走同一个 request()，自动带 Authorization 头，统一解析 {code, message, data}。数据一变，页面自己重绘，整页不刷新。

加 ?demo=1 自动跑演示，本来是为了用无头浏览器验证按钮真的能点，后来发现它还是个挺好用的分享链接。实测 13 步全部渲染，12 个 200 加 1 个预期中的 401，演示创建的文章最后自动删掉，数据回到 8 篇。

六、三层测试，各管一段

这次的验证分了三层，各有各的存在理由：

  • 11 个 JUnit 5 + MockMvc：在进程内模拟 HTTP，不起端口、用独立内存库，验证上下文能起、JWT 校验、CRUD 生命周期、缓存 HIT。
  • 23 条 Python 端到端回归：真的走网络、真的写库、真的读回来，验证 JSON 序列化、拦截器写出的真实 401、删除后 404、重置。
  • 无头浏览器 + ?demo=1：验证 Vue 挂载、fetch 真的发出去、DOM 真的更新，桌面和 500px 手机端各截一张图。

三个数字：Tests run: 11, Failures: 0、23 条 / 23 通过 / 0 失败、13 步浏览器演示全渲染。

这里又复用了一个跨项目的经验：机器上有全局 HTTP_PROXY，Python 的 urllib 默认会走代理，把 127.0.0.1 的请求也转发出去，拿回来的是代理的 404 而不是自家接口。项目 4 为这个折腾过一次，这次我在 e2e_api.py 里一开始就写了 ProxyHandler({})，curl 验证也一律加 --noproxy '*'。坑写进文档，下次才不用再踩一遍。

七、写在最后

这个项目做完，我最踏实的变化不是「会写 SpringBoot 了」，而是：再看到任何后端项目，我脑子里先出现的是那条固定链路——谁接请求、谁定规则、谁翻译 SQL、谁存数据、哪一步可以抄近路（缓存）、哪一步必须验身份（安检口）。框架只是把这条链路上的零件换了个名字。

按两周计划，Java 方向先做了博客系统，因为它和前四个 Web 项目能连成一条线：交易 → 消息可靠性 → 文件上传 → 接口测试 → 换语言重做同一套骨架。简历上摆出来，是一条「从业务功能到工程质量、再到跨语言迁移」的路线，而不是五个互不相干的小 demo。

剩下还没做的，我都不打算藏：真 MySQL、BCrypt、JWT 黑名单、文章归属校验、深分页优化。技术文档第 15 节列成了一张表。下次有人问「你这个项目能上线吗」，我希望自己的回答是「哪些能、哪些还差、为什么先不做」，而不是一句含糊的「差不多吧」。
